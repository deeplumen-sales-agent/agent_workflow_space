# PRD 撰写工作流

## 目标

把粗略想法、调研结果或技术底稿整理成业务、产品和研发都能执行的需求文档。PRD 中必须区分事实、决策、假设和待确认事项。

## 步骤

1. **确认任务边界**：写出目标用户、触发场景、要解决的问题、不在范围内的内容和完成标准。
2. **整理证据**：列出已有数据、访谈、页面、接口、代码和限制，并给每项标注状态和来源。
3. **定义业务对象**：为关键实体、身份、状态、关系和生命周期保留稳定名称；中英文名称同时出现时，保持一一对应。
4. **描述主流程**：按触发、输入、判断、动作、输出和异常写出端到端流程。
5. **拆分需求**：分别写功能、规则、权限、数据、状态转换、验收标准和非目标。
6. **处理不确定性**：将未确认的费率、日期、资格、接口行为或部署状态标记为 `pending_confirmation` 或 `unverified`，不做无依据的补全。
7. **编写验收标准**：每条验收标准都要有前置条件、操作、预期结果和证据方式。
8. **评审**：检查范围、术语、状态、异常、数据归属、权限、回滚和运营动作是否一致。

## 输出规则

- 先写结论和用户价值，再写实现细节。
- 商家和业务读者看到的正文使用业务语言；内部实现名放在技术说明或附录。
- 每个关键结论都应能回到来源或明确标记为提议。
- 不把“可以测试”写成“已上线”，不把“请求成功”写成“业务完成”。

## 正文排版规则

> 状态：`confirmed`（2026-11-06 用户确认）。来源：SHOPLINE 一期与通用 AP 二期需求评审会话；参照飞书「02 需求文档」第 1–6 章的写法。适用范围：`workflow:prd-writing`，含评审意见、对齐清单等起草需求文字的场合。

- **先按维度分，再分层**：同一节内容先按维度拆开（如 为什么 / 商家看到什么、做什么 / 系统做什么 / 首次出现的对象 / 规则 / 异常 / 例子），每个维度下再分子点。
- **每层开头一个加粗短标题**：用几个词说清这一层讲什么，例如 **为什么**、**商家看到什么**、**规则**、**异常**；不用整句当标题。
- **一点一句话**：每个分点是一句完整的话、只写一条需求或一个事实；一点里写不下就拆成多点，不在分点里堆长段落。
- **业务语言在正文**：技术名放括号里，或单独放在加粗的 **技术口径** 层。

示例：

```markdown
**为什么**
- 商家需要知道哪些商品会被 AI 读到。

**规则**
- 只读取已发布的商品。
- 设了访问密码的商品不读取。
```
